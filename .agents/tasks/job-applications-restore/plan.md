## Design decisions (fixed; don't re-decide)

- **D1. Semantics: job applications, not DUCC's "software requests".** The user asked for "job applies". DUCC had repurposed the collection as Software/IT-service requests (labels, `requestType`, student/faculty `workStatus`). We restore the job-application meaning and keep the old column names (`applicant_name, email, phone, job_title, current_address, permanent_address, highest_qualification, work_status, year_of_experience, resume_id, status, submitted_at`).
  - `requestType` (and its `enum_job_applications_request_type`) is dropped.
  - `workStatus` options are `fresher` and `experienced`. FormBuilderEmbed's existing "experienced → years of experience" logic and DUCC's `ROLE_LABELS` already use these values.
  - Status options are `new`, `reviewed`, `shortlisted` (label "Shortlisted"), `rejected`. `deleted` is not a stored status. In the dashboard it is a "Delete" action (see D5).
- **D2. Access.** All checks reuse `src/access/roles.ts` helpers; no new role predicates.
  - `job-applications`:
    - create = `siteAdminAccess`, so admins can still add an entry by hand. The public creates ONLY through `/api/apply`, which validates input and then writes with `overrideAccess: true`. An unauthenticated `POST /api/job-applications` therefore returns 403.
    - read, update and delete = `siteAdminAccess`. Delete is site-admin rather than super-admin only because Admins already manage forms and form submissions (also PII) with `siteAdminAccess`.
    - `admin.hidden = hiddenUnlessSiteAdmin`.
  - `resumes`:
    - create = `() => false` (documented), so the only creation path is `/api/apply`.
    - read, update and delete = `siteAdminAccess`, so files are not publicly downloadable. Payload's `/api/resumes/file/:filename` enforces collection read access.
    - `admin.hidden = hiddenUnlessSiteAdmin`.
  - Neither slug is added to `authorAssignableCollections`.
- **D3. Server-owned fields.** A `beforeChange` hook on `job-applications` handles create:
  - It always sets `submittedAt = new Date().toISOString()`.
  - It forces `status = 'new'` unless `isSiteAdmin(req.user)`.
  - `submittedAt` is `admin.readOnly`, with field-level `access.update: () => false`.
- **D4. Resume size and type limits.** Enforced in three places:
  1. In `/api/apply`: `Content-Length` > 6 MB gives 413; then `file.size` ≤ 5 MB, `file.type === 'application/pdf'`, and the first bytes must be `%PDF-`.
  2. In the `resumes` collection: a `beforeOperation` hook throws `APIError('Resume must be 5 MB or smaller.', 413)` when `req.file?.size > 5 * 1024 * 1024` on create/update.
  3. Also in the `resumes` collection: `upload.mimeTypes: ['application/pdf']`.

  The stored filename is generated by the server (`resume-<Date.now()>-<8 random hex>.pdf`) and never comes from the applicant's input.
- **D5. Delete cascade.** We replace DUCC's `autoDeleteWhenMarkedDeleted` afterChange hook, which deleted the doc from inside its own update.
  - Instead, a `beforeDelete` hook on `job-applications` reads the doc (`req` passed, depth 0) and deletes the linked resume (`req` passed, `overrideAccess: true` with a comment: the job-application delete was already authorized), so no orphan PDF remains.
  - The dashboard's "Delete" option sends `DELETE /api/job-applications/:id` after a `window.confirm`. The confirm is a small, deliberate addition for PII deletion.
- **D6. Public submit path: restore DUCC's.**
  - Re-add DUCC's `resumeUpload` custom field block to `formBuilderPlugin.fields` in `payload.config.ts`, so editors can put a PDF upload in a Form Builder form.
  - FormBuilderEmbed's existing (currently dead) `resumeUpload` UI becomes live again. When a form contains a `resumeUpload` field, the embed POSTs multipart `FormData` to `/api/apply` (Next route `src/app/api/apply/route.ts`, same style as `src/app/api/invitations/accept/route.ts`).
  - Forms without a `resumeUpload` field keep posting JSON to `/api/form-submissions`, unchanged.
  - The hardcoded "Year of Experience" input is removed. Editors add their own field named or labelled like `yearOfExperience` / "Years of experience", which is matched by hint.
  - Visitor flow: CareerPosting "Apply" button → a CMS page (e.g. slug `apply`) containing a FormLayout block whose form has a `resumeUpload` field → submit → `/api/apply`. CareerPostingBlock's fallback href `/applicant/login` (no such route) becomes `/apply`, matching the field's admin description.
  - The schema change for this: new table `forms_blocks_resume_upload`.
- **D7. Admin UI, registered as DUCC did, plus the view and nav link the task lists.**
  - `admin.components.afterDashboard: ['@/components/admin/ApplicationsDashboardCard#ApplicationsDashboardCard']`. This is the collapsible widget on `/admin`.
  - `admin.components.views.applicationsDashboard = { Component: '@/components/admin/ApplicationsDashboard#ApplicationsDashboard', path: '/applications' }`. This is the full-page view at `/admin/applications`, wrapped in `DefaultTemplate` from `@payloadcms/next/templates` with `Gutter` from `@payloadcms/ui`.
  - `admin.components.afterNavLinks: ['@/components/admin/ApplicationsNavLink#ApplicationsNavLink']`.

  Gating and data access:
  - Every component renders nothing (client) or a "You do not have access" message (server view) unless `isSiteAdmin(user)`. Client components use `useAuth()` from `@payloadcms/ui`. The server view uses `initPageResult.req.user`.
  - Data: the view calls `payload.find({ collection: 'job-applications', user: initPageResult.req.user, overrideAccess: false, depth: 1, limit: 200, sort: '-createdAt' })`. The client and card call REST `/api/job-applications…` with `credentials: 'include'`.
  - No custom Payload endpoint is added. `/api/apply` is a public Next route that never returns application data.

  Look and behaviour:
  - Same as DUCC: inline styles, colours, stat cards, filters, search, table, status pill select, CSV/Excel export, resume download link.
  - Copy changes to job wording ("Job Applications", "Applicant", "Position", "Experience"). The card's Software/IT-service tab bar is removed, since there is no `requestType` (D1). Everything else in the card stays.
  - Accessibility, matching the earlier site work: `type="button"` on buttons, `aria-label` on the search input and on each row's status select (`Status for <name>`), `scope="col"` on `th`, `aria-expanded` + `aria-controls` on the card toggle, decorative emoji wrapped in `aria-hidden`, failure messages in a `role="alert"` element. DUCC's `throw` inside `startTransition` is replaced by setting that error.
- **D8. PII on disk.** Add `/resumes/` to `.gitignore`. `CMS_RESUMES_UPLOAD_DIR` (default `resumes`) sits outside `public/`, so files are only served through Payload's access-checked route.
- **D9. Validation is a pure module** (`src/lib/jobApplications/validateApplication.ts`) so it can be unit-tested with vitest without a DB.
- **D10. Workflow shape.** Not restructured into FEATs. This is one sequential piece of work: config → types → schema apply → route/UI → runtime checks, and every step depends on the previous. The existing implement/review loop runs this plan, and its stop contract (`review.json` → `verdict` = `APPROVED`) is unchanged.

Known gaps and assumptions:
- There is no rate limiting or CAPTCHA on `/api/apply` (same as DUCC and the Form Builder submissions endpoint). Note this in the verification note as a follow-up; don't add it.
- `localized: true` on the `resumeUpload` label is harmless because no localization is configured.
